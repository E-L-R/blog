# Domain Model

> **Status:** partly built. `User` is built, and so is `Post`, apart from its TL;DR and like-count fields. Comments, likes and the AI features are still design, and there are no endpoints yet. Parts that are not built yet are marked *planned*, with the roadmap step that adds them.

This document describes the entities, their rules and the main flows. Related documents:
- [ARCHITECTURE.md](ARCHITECTURE.md): modules, events and the AI worker
- [DATABASE.md](DATABASE.md): tables, constraints and indexes
- [API.md](API.md): the REST endpoints

## Overview

Database view (every arrow is a real foreign key):

```
users 1───* posts 1───* comments ─┐
  │           │           │   ▲   │ parent_id (0..1)
  │           │           │   └───┘
  ├──* post_likes *──1 posts
  ├──* comment_likes *──1 comments
  └──* ai_requests ──► posts / comments (target), comments (result)
```

Which module owns each entity, and how it refers to entities in other modules:

| Entity | Module | References inside the module | References to other modules (by ID) |
|---|---|---|---|
| User | `user` | | |
| Post | `post` | | `authorId` |
| Comment | `comment` | `parent` | `postId`, `authorId` |
| PostLike | `like` | | `userId`, `postId` |
| CommentLike | `like` | | `userId`, `commentId` |
| AiRequest | `ai` | | `requestedById`, `postId`, `commentId`, `resultCommentId` |

## Design principles

- **Reference other modules by ID.** JPA relationships (`@ManyToOne`) are only used inside a module. Across modules, an entity stores the UUID, and the schema still has a real foreign key. This keeps the database's integrity without coupling one module's entities to another's, and avoids lazy loading across module boundaries.
- **Like rows are the source of truth.** `likeCount` fields are caches, updated atomically in the same transaction as the like row.
- **One writer per column.** A column is written either through JPA or through a targeted SQL statement, never both. Columns written by SQL (`likeCount`, the TL;DR columns) are mapped read-only in JPA, so saving an entity can never overwrite them with a stale value. See [DATABASE.md](DATABASE.md#columns-written-by-sql).
- **Derive state instead of storing it twice.** Whether a post's TL;DR is up to date is computed from hashes, not kept in a separate status column that could disagree.
- **No collections on User.** User has no `posts` or `comments` collections. The module that owns the data answers instead, for example `PostService.listByAuthor`.
- **AI output is written by a bot User,** so a comment always has an author.
- **LLM calls are asynchronous** and tracked by `AiRequest`.
- **Times are `Instant` (UTC), taken from an injected `Clock`. IDs are UUIDv7,** generated by Hibernate when an entity is first saved (see [D15](DECISIONS.md#d15-ids-are-uuidv7-generated-by-hibernate)).

# Entities

## User
#### fields:
- id (UUID)
- email (unique; stored in lower case; null for the bot and for deleted accounts)
- username (unique, ignoring case; displayed as entered; kept after deletion so it is never reused)
- passwordHash (null for the bot and for deleted accounts)
- role (enum: USER, BOT)
- deletedAt (Instant, nullable; set when the account is deleted)
- createdAt (Instant)

#### methods:
- isBot()
- isDeleted()
- delete(now): clears `email` and `passwordHash` and sets `deletedAt`. Rejected for the bot. Deleting an already deleted account changes nothing.

#### rules:
- The bot user is created by a Flyway migration with a fixed, well-known UUID. Its username is reserved simply because its row exists.
- A user has an email and a password hash if and only if it is a regular user whose account is not deleted (enforced by check constraints). So neither the bot nor a deleted account can ever log in.
- Deleting an account works the way Reddit does it (see [Delete an account](#flows)). The row stays as a tombstone, so everything that refers to the user stays valid.
- `UserService` returns public user views only for accounts that are not deleted. So `post` and `comment` show a missing author ("[deleted]") without knowing anything about deletion.
- `UserService.create` takes a password **hash**. Hashing belongs to `auth`, so the `user` module never sees a password.
- `UserService` has no delete method yet. It comes with the `auth` step, which checks the password first (*planned*).

## Post
#### fields:
- id (UUID)
- authorId (UUID → users)
- title
- content
- contentHash (SHA-256 of `content`; updated whenever the content changes) *(planned: `ai` step)*
- tldr (nullable; the most recent TL;DR, possibly for older content) *(planned: `ai` step)*
- tldrSourceHash (nullable; the `contentHash` that `tldr` was generated from) *(planned: `ai` step)*
- tldrGeneratedAt (Instant, nullable) *(planned: `ai` step)*
- tldrFailedHash (nullable; the `contentHash` for which generation failed for good) *(planned: `ai` step)*
- likeCount (cache) *(planned: `like` step)*
- version (optimistic locking)
- createdAt (Instant)
- updatedAt (Instant)

`tldr`, `tldrSourceHash`, `tldrGeneratedAt`, `tldrFailedHash` and `likeCount` will be read-only in JPA. They are written only by the SQL statements described below.

#### methods:
- Post(authorId, title, content, now): rejects a blank title or content with `IllegalArgumentException`, and sets `createdAt` and `updatedAt`.
- edit(title, content, now): updates both fields and `updatedAt`, with the same checks. *Planned for the `ai` step:* it also updates `contentHash` and returns whether the content changed. If it did, the service publishes `PostContentChangedEvent`. Title-only edits do not regenerate the TL;DR, because the TL;DR summarises the content only.
- isAuthoredBy(userId)
- tldrStatus() *(planned: `ai` step)*: derived, never stored:
  - `GENERATED` if `tldrSourceHash == contentHash`
  - otherwise `FAILED` if `tldrFailedHash == contentHash`
  - otherwise `PENDING`

#### TL;DR writes (by the `ai` module, through `PostService`):
*Planned for the `ai` step.*

- applyTldr(postId, tldr, sourceHash): sets `tldr`, `tldrSourceHash` and `tldrGeneratedAt`, but only if `sourceHash` still equals the post's `contentHash`. It is a single `UPDATE ... WHERE id = ? AND content_hash = ?`. If the post was edited since the job read it, nothing is written, and the job for the newer content produces the right TL;DR.
- markTldrFailed(postId, sourceHash): sets `tldrFailedHash`, with the same condition.

Because the condition is part of the `UPDATE` statement, it is also safe against an edit that is happening at the same moment: Postgres makes the `UPDATE` wait for the edit to commit and then re-checks the condition against the new content.

#### rules:
- Only an account that exists and is not deleted can write a post. Otherwise `PostService.create` throws `AuthorNotFoundException`.
- Only the author can edit or delete a post (`NotAuthorException`; a missing post gives `PostNotFoundException`). If the author deletes their account, the post stays, with the author shown as "[deleted]", and nobody can edit or delete it any more.
- Posts are listed newest first, with the ID breaking ties so pages stay stable. Listing a deleted account's posts returns an empty page, but each post can still be read by its ID.
- The previous `tldr` stays visible while a new one is `PENDING`. Clients can show it as "updating". *(planned: `ai` step)*

## Comment
*Planned for the `comment` step.*

Comments form a tree through `parent`. Every comment also stores its `postId`, so a whole thread loads in one query.

#### fields:
- id (UUID)
- postId (UUID → posts)
- parent → Comment (nullable; null = top-level comment)
- authorId (UUID → users; may be the bot user)
- content (null if and only if the comment is deleted)
- likeCount (cache; read-only in JPA)
- deleted (boolean, soft delete)
- version (optimistic locking)
- createdAt (Instant)
- updatedAt (Instant)

#### methods:
- reply(authorId, content): creates a child Comment with the same `postId`. Rejected if this comment is deleted.
- edit(content): rejected if the comment is deleted
- softDelete(): sets `deleted = true` and clears `content`. The row stays so replies remain attached; clients render it as "[deleted]". Deleting an already deleted comment changes nothing.
- isTopLevel()

#### rules:
- A reply always has the same `postId` as its parent. `reply()` enforces it, and so does the schema (a composite foreign key, see [DATABASE.md](DATABASE.md#comments)).
- A reply that races with the deletion of its parent may still be saved. That is harmless, because deleted comments keep their replies anyway.
- Only the author can edit or delete a comment. Nobody can edit or delete bot comments, or the comments of a deleted account.
- There is no limit on nesting depth.

## AiRequest
*Planned for the `ai` step.*

Tracks every LLM call. The table is also the job queue (see [ARCHITECTURE.md](ARCHITECTURE.md#async-ai-processing)) and an audit trail. The application never deletes these rows (a retention job may come later; see [OPERATIONS.md](OPERATIONS.md#database-maintenance)).

#### fields:
- id (UUID)
- type (enum: TLDR, REPLY)
- status (enum: PENDING, IN_PROGRESS, COMPLETED, FAILED, CANCELLED)
- requestedById (UUID → users, nullable; null for system-triggered TL;DRs)
- postId (UUID → posts; set at creation, becomes null if the post is deleted)
- commentId (UUID → comments, nullable; the comment the user invoked the AI on, null if invoked on the post)
- resultCommentId (UUID → comments, nullable; the bot's reply once a REPLY completes)
- model (nullable; the model identifier used, set when the LLM is called)
- attempts (int; how many times the job was claimed)
- nextAttemptAt (Instant; when the job may next be claimed)
- lockedUntil (Instant; the lease of the worker processing it; set only while IN_PROGRESS)
- error (nullable; the last error, for operators only)
- createdAt (Instant)
- completedAt (Instant, nullable; set when the request reaches a final status)

When a post is deleted, `postId`, `commentId` and `resultCommentId` are set to null by the database (`ON DELETE SET NULL`), but the row stays, which keeps the audit trail.

#### state machine:

| From | When | To |
|---|---|---|
| PENDING | claimed by a worker once `nextAttemptAt` is reached | IN_PROGRESS |
| IN_PROGRESS | the lease expired and another worker claims it again | IN_PROGRESS |
| IN_PROGRESS | the LLM call succeeded and the result was written | COMPLETED |
| IN_PROGRESS | retryable error, attempts left | PENDING (`nextAttemptAt` = now + backoff) |
| IN_PROGRESS | other error, or no attempts left | FAILED |
| PENDING, IN_PROGRESS | the target is gone or deleted, or the TLDR request is superseded | CANCELLED |

- A job whose lease expired but has no attempts left (for example, because it crashed its worker every time) becomes `FAILED` instead of being claimed again.
- `COMPLETED`, `FAILED` and `CANCELLED` are final.

#### methods:
Every transition out of IN_PROGRESS clears `lockedUntil`.
- claim(now, leaseDuration): → IN_PROGRESS, increments `attempts`, sets `lockedUntil`
- isHeldBy(attempt): true if the status is IN_PROGRESS and `attempts` still equals the attempt number the worker claimed. The worker checks this before writing a result, so a worker whose lease expired cannot overwrite the work of the one that took over.
- complete(resultCommentId?, model): → COMPLETED, sets `completedAt`
- retryLater(error, nextAttemptAt): → PENDING, records the error
- fail(error): → FAILED, sets `completedAt`
- cancel(reason): → CANCELLED, sets `completedAt`
- canRetry(maxAttempts)

#### invariants:
- type = TLDR ⇒ `requestedById`, `commentId` and `resultCommentId` are null
- type = REPLY ⇒ `requestedById` is not null
- type = REPLY and status = COMPLETED ⇒ `resultCommentId` is not null, unless the post was deleted afterwards
- A TLDR request is **superseded** when a newer TLDR request exists for the same post, whatever that request's status. Every content change creates a new request in the same transaction, so if no newer request exists, the post's content has not changed since this request was created.

# Flows

**Create or edit a post (TL;DR):**
*Planned for the `ai` step. Today, creating or editing a post only saves it.*

1. The post is saved, and `PostCreatedEvent` or `PostContentChangedEvent` is published. In the same transaction, the `ai` module inserts `AiRequest(type=TLDR)`.
2. The worker claims the job. If it is superseded, the worker cancels it without calling the LLM.
3. Otherwise the worker reads the content, computes its hash and calls the LLM. Then:
   - success → `applyTldr(postId, tldr, hash)` and `request.complete()`. If the post was edited in the meantime, the hash condition discards the result, and the newer job produces the right TL;DR.
   - retryable error with attempts left → `request.retryLater(...)`
   - any other error → `request.fail(...)` and `markTldrFailed(postId, hash)`

Quick successive edits create several jobs, but only the newest one calls the LLM, unless an older one was already running.

**AI reply:**
*Planned for the `ai` step.*

1. A user calls `POST /posts/{id}/ai-reply` or `POST /comments/{id}/ai-reply`. The target must exist, and a comment must not be deleted.
2. Insert `AiRequest(type=REPLY)`. AI use is not limited: a user may ask as often as they like.
3. Respond `202 Accepted` with the request. The requester can poll `GET /ai-requests/{id}` for the status and `resultCommentId`.
4. The worker claims the job, builds the prompt (see [ARCHITECTURE.md](ARCHITECTURE.md#prompt-construction)) and calls the LLM. If the post is gone or the target comment is deleted, it cancels the request instead.
5. In one transaction: lock the request row, check `isHeldBy(attempt)`, check the target again, then the bot user creates the comment (a reply to the target comment, or a top-level comment on the post) and the request is completed. If the post was deleted at that moment, the insert fails on its foreign key, and the worker cancels the request.

Users may also ask the AI to reply to a bot comment. Bot loops are impossible, because only users create AI requests.

**Like / unlike:** *(planned: `like` step)* The target must exist, and a comment must not be deleted. In one transaction:
- like → `INSERT ... ON CONFLICT (user_id, post_id) DO NOTHING`. If a row was inserted, run `UPDATE posts SET like_count = like_count + 1`.
- unlike → `DELETE`. If a row was deleted, run `UPDATE posts SET like_count = like_count - 1`.

Both are idempotent: liking twice or unliking something not liked changes nothing. Catching the duplicate-key exception instead would not work, because in Postgres an error aborts the whole transaction. Comment likes work the same way.

**Delete a post:** A hard delete. The schema's foreign keys delete the post's comments and likes with it (`ON DELETE CASCADE`) and detach its AI requests (`ON DELETE SET NULL`). The `post` module does not need to know about the other modules. The worker cancels any unfinished request whose `postId` is now null. *Today only the post row is deleted; the cascades arrive with the comment, like and AI request tables.*

**Delete a comment:** *(planned: `comment` step)* A soft delete (see `Comment.softDelete()`). Its likes and replies stay. Unfinished AI replies to it are cancelled when the worker picks them up.

**Delete an account** (the way Reddit does it):
*`User.delete` is built; the endpoint and the password check come with the `auth` step.*

1. The user calls `POST /me/delete` with their password. A valid token alone is not enough: the password confirms that the account owner is asking.
2. In one transaction, `user.delete(now)` clears the email and password hash and sets `deletedAt`. Nothing else is written:
   - The account's posts and comments stay, with the author shown as "[deleted]". Users who want their content gone must delete it before deleting the account, as on Reddit.
   - Its likes stay, so like counts don't change.
   - Its unfinished AI requests still run. The bot's reply belongs to the bot, not to the deleted account.
   - Its profile (`GET /users/{id}`) returns `404`, and its posts are no longer listed by author.
   - The username is retired: nobody, including the same person, can register it again. The email is freed, so the person can sign up again with it under a new username.
3. All of the account's tokens stop working at once, because every request with a token checks that its account is not deleted (see [ARCHITECTURE.md](ARCHITECTURE.md#security)).

Deleting an account is permanent; it cannot be restored. The bot cannot be deleted.
