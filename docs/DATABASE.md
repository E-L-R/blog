# Database

> **Status:** partly built. The `users` table (`V1__create_users.sql`) and the `posts` table (`V2__create_posts.sql`, without its TL;DR and like-count columns) exist. The other tables and columns are design, marked *planned* with the roadmap step that adds them.

PostgreSQL is the only data store. Flyway owns the schema, and Hibernate only validates it (`spring.jpa.hibernate.ddl-auto=validate`). This document describes the tables, their constraints and indexes, and the few statements that are written in SQL instead of going through JPA. The entities and their behaviour are in [DOMAIN.md](DOMAIN.md).

## Conventions

| Concern | Convention |
|---|---|
| Names | `snake_case`, plural table names (`posts`, `post_likes`) |
| Constraint and index names | Every constraint and index is named, because the name appears in error messages: `<table>_<columns>_key` (unique), `_fkey` (foreign key), `_idx` (index). A check constraint is named after the rule it enforces, such as `users_bot_not_deleted`. |
| IDs | `uuid`, generated by the application (UUIDv7, see [D15](DECISIONS.md#d15-ids-are-uuidv7-generated-by-hibernate)) |
| Times | `timestamptz`, always UTC |
| Enums | `varchar` with a `CHECK` constraint listing the allowed values (`@Enumerated(EnumType.STRING)` in JPA) |
| Hashes | `char(64)`: hex-encoded SHA-256 |
| Optimistic locking | `version bigint` on tables that users edit (`posts`, `comments`) |
| Foreign key columns | always indexed, so cascades and `SET NULL` don't scan whole tables |

Local development (`compose.yaml`) and the tests (`TestcontainersConfiguration`) both use the `postgres:18` image; change them together. Nothing here needs a recent PostgreSQL release.

## Tables

`→` marks a foreign key, followed by its `ON DELETE` action. User rows are never removed: deleting an account keeps the row as a tombstone (see [DOMAIN.md](DOMAIN.md#user)). So foreign keys to `users` use the default (`RESTRICT`), and everything a deleted account created keeps a valid reference.

### users

| Column | Type | Null | Notes |
|---|---|---|---|
| id | uuid | no | primary key |
| email | varchar(254) | yes | unique (`users_email_key`); stored in lower case (`users_email_lower_case`) |
| username | varchar(30) | no | unique ignoring case: unique index `users_username_lower_key` on `lower(username)`. Kept after deletion, so it is never reused. |
| password_hash | varchar(100) | yes | bcrypt hash |
| role | varchar(10) | no | `USER` or `BOT` (`users_role_check`) |
| deleted_at | timestamptz | yes | set when the account is deleted |
| created_at | timestamptz | no | |

- `users_email_presence`: `CHECK ((email IS NULL) = (role = 'BOT' OR deleted_at IS NOT NULL))`, and `users_password_presence` does the same for `password_hash`. Only regular accounts that are not deleted have an email and a password, so neither the bot nor a deleted account can log in. Unique constraints ignore nulls, so any number of deleted accounts can be without an email.
- `users_bot_not_deleted`: `CHECK (role <> 'BOT' OR deleted_at IS NULL)`, so the bot cannot be deleted.
- `UserService.create` refers to `users_email_key` and `users_username_lower_key` by name. When two registrations happen at the same moment, the database refuses the second one, and the service reads the name of the violated constraint to answer `EMAIL_TAKEN` or `USERNAME_TAKEN`. A migration that renames either one must change the service too.
- The bot user is inserted by `V1__create_users.sql` with the fixed ID `00000000-0000-0000-0000-000000000001` and the username `blog-ai`. The same ID is the constant `UserService.BOT_USER_ID`.

### posts

| Column | Type | Null | Notes |
|---|---|---|---|
| id | uuid | no | primary key |
| author_id | uuid | no | → users (`posts_author_fkey`) |
| title | varchar(200) | no | |
| content | text | no | |
| content_hash | char(64) | no | SHA-256 of `content`. *Planned: `ai` step.* |
| tldr | text | yes | written by SQL. *Planned: `ai` step.* |
| tldr_source_hash | char(64) | yes | written by SQL. *Planned: `ai` step.* |
| tldr_generated_at | timestamptz | yes | written by SQL. *Planned: `ai` step.* |
| tldr_failed_hash | char(64) | yes | written by SQL. *Planned: `ai` step.* |
| like_count | integer | no | default 0, `CHECK (like_count >= 0)`, written by SQL. *Planned: `like` step.* |
| version | bigint | no | default 0 |
| created_at | timestamptz | no | |
| updated_at | timestamptz | no | |

Indexes:
- `posts_created_at_idx` on `(created_at)`: the post list, newest first. Posts with the same `created_at` are then sorted by `id`.
- `posts_author_id_created_at_idx` on `(author_id, created_at)`: posts by one author, and the foreign key

### comments

*Planned for the `comment` step.*

| Column | Type | Null | Notes |
|---|---|---|---|
| id | uuid | no | primary key |
| post_id | uuid | no | → posts, `CASCADE` |
| parent_id | uuid | yes | → comments, `CASCADE` (composite key, see below) |
| author_id | uuid | no | → users |
| content | text | yes | null once deleted |
| deleted | boolean | no | default false |
| like_count | integer | no | default 0, `CHECK (like_count >= 0)`, written by SQL |
| version | bigint | no | default 0 |
| created_at | timestamptz | no | |
| updated_at | timestamptz | no | |

- **Replies stay on their parent's post:** `UNIQUE (id, post_id)`, and the parent foreign key is `FOREIGN KEY (parent_id, post_id) REFERENCES comments (id, post_id)`. A reply whose `post_id` differs from its parent's is rejected by the database. Top-level comments have a null `parent_id`, so the key is not checked for them.
- `CHECK (deleted = (content IS NULL))`: a comment has content if and only if it is not deleted.

Indexes:
- `(post_id, created_at)`: loading a thread in order, and the foreign key
- `(parent_id)`: the parent foreign key
- `(author_id)`: the foreign key

### post_likes

*Planned for the `like` step.*

| Column | Type | Null | Notes |
|---|---|---|---|
| id | uuid | no | primary key |
| user_id | uuid | no | → users |
| post_id | uuid | no | → posts, `CASCADE` |
| created_at | timestamptz | no | |

- `UNIQUE (user_id, post_id)`: one like per user. This index also answers "which of these posts has this user liked?".
- Index `(post_id)`: the foreign key.

### comment_likes

*Planned for the `like` step.*

The same as `post_likes`, with `comment_id` (→ comments, `CASCADE`) instead of `post_id`:
- `UNIQUE (user_id, comment_id)`
- Index `(comment_id)`

### ai_requests

*Planned for the `ai` step.*

| Column | Type | Null | Notes |
|---|---|---|---|
| id | uuid | no | primary key |
| type | varchar(10) | no | `TLDR` or `REPLY` |
| status | varchar(12) | no | `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED` or `CANCELLED` |
| requested_by | uuid | yes | → users |
| post_id | uuid | yes | → posts, `SET NULL` |
| comment_id | uuid | yes | → comments, `SET NULL` |
| result_comment_id | uuid | yes | → comments, `SET NULL` |
| model | varchar(100) | yes | |
| attempts | integer | no | default 0, `CHECK (attempts >= 0)` |
| next_attempt_at | timestamptz | no | |
| locked_until | timestamptz | yes | |
| error | text | yes | |
| created_at | timestamptz | no | |
| completed_at | timestamptz | yes | |

The application never deletes rows. When a post is deleted, its requests keep their history; only their references become null.

Check constraints:
- `type <> 'TLDR' OR (requested_by IS NULL AND comment_id IS NULL AND result_comment_id IS NULL)`
- `type <> 'REPLY' OR requested_by IS NOT NULL`
- `(status = 'IN_PROGRESS') = (locked_until IS NOT NULL)`: only a running job has a lease
- `(status IN ('COMPLETED', 'FAILED', 'CANCELLED')) = (completed_at IS NOT NULL)`

Indexes:
- `(next_attempt_at) WHERE status = 'PENDING'`: finding due jobs
- `(locked_until) WHERE status = 'IN_PROGRESS'`: finding expired leases
- `(requested_by)`: the foreign key
- `(post_id, created_at)`: the "superseded" check for TL;DR jobs, and the foreign key
- `(comment_id)` and `(result_comment_id)`: the foreign keys

## Foreign keys between modules

Modules refer to each other's entities by ID, so these foreign keys exist only in the schema, not as JPA relationships. Two consequences:
- Hibernate cannot order inserts by them. It writes inserts in the order the entities were persisted (keep `hibernate.order_inserts` off), so the referenced row must be persisted first. The flows already do this: a post is saved before its `AiRequest`, a comment before its likes.
- A foreign-key error caused by a concurrent delete (for example, liking a post while it is being deleted) is mapped to `404 Not Found`, not `500`.

## Columns written by SQL

*Planned: these columns arrive with the `like` and `ai` steps.*

These columns are mapped read-only in JPA (`@Column(insertable = false, updatable = false)`). Hibernate updates every mapped column when it saves an entity, so without this rule, saving a post that was loaded before a like would write back the old `like_count`.

| Column | Written by | How |
|---|---|---|
| `posts.like_count`, `comments.like_count` | `like`, through `PostService` / `CommentService` | `like_count = like_count + 1` or `- 1`, in the same transaction as the like row |
| `posts.tldr`, `tldr_source_hash`, `tldr_generated_at` | `ai`, through `PostService.applyTldr` | `UPDATE ... WHERE id = ? AND content_hash = ?` |
| `posts.tldr_failed_hash` | `ai`, through `PostService.markTldrFailed` | the same condition |

After such a statement, an entity already loaded in the same transaction still holds the old value. Re-read it if the new value is needed.

## Other statements written in SQL

*Planned for the `like` and `ai` steps.*

- **Likes:** `INSERT ... ON CONFLICT DO NOTHING` and `DELETE`, each reporting whether a row changed (see [DOMAIN.md](DOMAIN.md#flows)).
- **Claiming jobs:** `SELECT ... FOR UPDATE SKIP LOCKED` over due jobs, ordered by `next_attempt_at`, with a limit. The current time is passed in from the application's `Clock` rather than using `now()`, so tests control it.

All of them use bind parameters.

## Migrations

- Location: `src/main/resources/db/migration`.
- Names: `V<number>__<description>.sql`, with two underscores, for example `V1__create_users.sql`.
- Done: `V1__create_users.sql` (users and the bot user), `V2__create_posts.sql`.
- Planned, in this order: comments; likes, plus `like_count` on posts and comments; ai_requests, plus the TL;DR columns on posts. Each migration creates one module's tables, constraints and indexes, or adds the columns a step needs.
- A column added to a table that already has rows needs a default (`like_count ... DEFAULT 0`) or a backfill in the same migration (`content_hash` must be computed for existing posts) before it can be `NOT NULL`.
- An applied migration is never edited. Changes always go in a new migration. V1 and V2 are on `main`, so they are final. While you are still writing a new migration, you can reset your local database and run it again (see [DEVELOPMENT.md](DEVELOPMENT.md#reset-the-local-database)).
- Flyway runs at application startup, before Hibernate validates the schema. Tests run the same migrations against a real PostgreSQL in Testcontainers, so the schema is tested on every build.
